# Bounded Pydantic AI investigation

The Learning job now runs a real asynchronous Pydantic AI agent with typed read-only tools, development evaluation, feedback and bounded revision. A final candidate is frozen and persisted before the trusted independent validator runs. Only independently accepted artifacts enter persistent agent memory; working proposals do not replace an accepted parent or activate simulator control.

The integration pins `pydantic-ai-slim[openai]==2.57.0` and Python 3.11, using the official [Crusoe integration](https://pydantic.dev/docs/ai/models/crusoe/) and [agent documentation](https://pydantic.dev/docs/ai/core-concepts/agent/). The [release metadata](https://pypi.org/project/pydantic-ai-slim/2.57.0/) and a clean installation of the complete lock were checked during implementation. Advertised provider features were checked separately with authenticated discovery and bounded live probes; documentation alone was not treated as evidence of working tool calls.

## Boundaries and versions

`investigator.py` constructs an `Agent[AgentDeps, CandidateDraft]`. Its frozen dependency object contains a read-only mapping of sanitized development evidence, a development-only evaluation capability, resource counters and an evidence emitter. It contains no simulator state, database, credentials, network client, arbitrary filesystem access or validation/final-set loader. The callback's fixed `TRAIN_SEEDS` cannot be supplied by a model. Python is not a security sandbox; the isolation is a narrow model tool capability boundary, plus a disposable worker process. Models cannot execute Python.

The registered tools inspect modeled dependencies, read cached occupancy/readiness observations, summarize development failures, and evaluate bounded counterfactual programs. Every result identifies its source, case, snapshot hash, freshness, units, uncertainty and availability. Cached missing observations remain unavailable. Concrete feedback includes delay/backlog changes, failed decision times and check identifiers, read counts, unread dependency types and links to development evidence. No hidden readiness/occupancy values enter diagnostics. Tool content is untrusted data. Unknown tools, extra arguments, unknown evidence IDs, oversized results and invalid output fail closed without paid repair retries.

Agent contracts use strict Pydantic validation, forbid extra keys and nonfinite values, and limit serialized payloads to 18 KB. There are at most four unique operations, eight evidence references and 400 explanation characters. Tools execute sequentially. Live Crusoe responses use native JSON-schema output (`NativeOutput`), the structured mode actually observed to return valid JSON. Fixture and general boundary tests use the `submit_candidate` output tool; additional native-mode tests cover the same strict local schema and investigation gate. Neither mode may skip required investigation. `FunctionModel` provides deterministic fixture runs; this is explicitly not live model inference. Tests use `FunctionModel`, `TestModel` and model overrides, with real network disabled.

## Policy capacity and compatibility

The original 65 ordered observation subsets have only five distinct development outcomes; the original strong static policy is globally best. The version 2 interpreter adds only bounded target selection (`all`, `pending`, `pending-first`) and iteration order (`tool-major`, `aircraft-major`). Its 390 programs yield 30 distinct outcomes, but still no development improvement over the original strong static. These results identify a planner/suite capacity ceiling, not an inability of Nemotron to learn. No scenarios, objective weights, safety limits or acceptance thresholds were tuned to force a win.

The initial pending-first hand-authored extension performed worse during the development-only capacity audit. The final strong comparator therefore keeps the original all/tool-major behavior, expressed with the version 2 grammar. Validation still requires improvement over that strong comparator and the accepted parent. The interpreter never changes fixed flight ordering, solver configuration, compulsory safety observations, reservations, verification, or objectives. Every optional read still consumes one of eight deployed reads. There is no executable code, arbitrary expression, SQL, recursion or graph loader in the grammar. Operation depth is one; runtime is bounded by four operations and the finite aircraft list, stopping after eight reads.

Version 1 programs retain their behavior and hashes: default version 2 fields are omitted when hashing legacy artifacts. Old policy and job payloads remain readable. Schema migration 1→2 is additive; historic research and evaluation artifacts are immutable. The old manual provider adapter remains for historical regression tests; active movement proposals cannot issue that single-shot paid path. Crusoe movement proposals require an already accepted agent artifact and still pass the ordinary independent verifier before explicit commit.

## Budgets, spend and cancellation

Default per-agent limits are six model requests, twelve investigation tool calls, four development evaluations (including initial parent evidence), one revision, 60,000 input tokens, 6,000 output tokens, 1,000 output tokens per request, 120 seconds and $0.02 reserved spend. Server contracts cap configurable values. These investigation budgets are separate from the eight deployed observation reads per scheduling decision. Identical programs reuse completed development results. Identical proposals, no new semantic feedback, exhausted limits and cancellation stop the loop.

Native `CrusoeModel`/`CrusoeProvider` use an injected managed `AsyncOpenAI` client and async HTTP transport. Authenticated model discovery checks the exact pinned NVIDIA ID, tool support, token bound, context and finite normalized pricing. The custom transport is only a spend/security boundary around the documented native model integration, not a replacement model implementation. It permits only the pinned HTTPS origin and chat completion path. Before every paid POST it bounds complete serialized input (including schemas/history), reserves conservative cost in the shared SQLite ledger and persists the reservation event. SDK, HTTP transport, framework output and tool-repair retries are all zero. Ambiguous, malformed, truncated, missing/inconsistent-usage, failed and interrupted responses retain their reservations. Verified actual cost never releases conservative reservations. Unknown final cost is labeled separately from verified cost.

The ledger transaction enforces both aggregate and per-job reservation limits. Its persisted approval ceiling cannot be increased by reopening a ledger with a higher cap. Budget ID and ledger location must remain shared across processes/deployments. The existing approved $0.05 aggregate cap and historical reservations remain in force; the new integration does not reset or raise them. Telemetry/instrumentation is not enabled. Raw prompts, model responses and credentials are not logged or exported.

The API owns one spawned process per job, with one active job permitted in the single-worker deployment. HTTP polling, simulation and comparison stay responsive. Cancellation terminates the entire process, including CPU evaluation and inference, then records a terminal event; completed evidence and reservations remain. A watchdog terminates overlong workers. Startup marks queued/running jobs interrupted. A transaction/version claim permits only queued→running once; terminal or already claimed jobs never replay paid work. Recovery reuses persisted evidence for inspection but deliberately starts no automatic inference. Frozen evidence is retained if validation is interrupted. Starting a fresh job is explicit.

## Validation, persistence and evaluation

The fixed legacy development/validation/final suites and event tapes remain unchanged. An agent sees development only. Each job records the exposure transition from development to validation after its frozen hash is persisted; no validation result returns to that agent's history. The final held-out set stays sealed in this adaptive workflow. Validation checks all-case feasibility, fixed observation/solver budgets, no more than 5% tail regression and at least 1% score improvement over both strong static and accepted parent. Rejected and accepted artifacts are both retained. Policy activation remains a separate explicit API command; rollback keeps its existing behavior.

Job journals record ordered typed events, lifecycle stages, parent/ancestry, schema/prompt/evaluator versions, tool evidence, candidates, development revisions, frozen hash, validation verdicts, resources and provider usage. Accepted memory updates atomically with final policy/job persistence. State export includes old and new jobs and policies; source-controlled OpenAPI and generated TypeScript are updated together.

Run `PYTHONPATH=backend .venv-agent/bin/python scripts/evaluate_agent.py`. The report compares matched FCFS, original-strength static, the historical single-proposal Nemotron program (explicitly replayed), stateless agent and persistent agent. Both agent arms have equal settings, tools and feedback budgets; only accepted-parent context differs. The first persistent run has no learned accepted ancestor. The raw report retains per-case metrics, event tapes, decisions, backlog/completions, feasibility, variability, solver time, latency, tools, evaluations, tokens and spend. `--live` uses only configured approved budget and never falls back to another provider. A small live sample is capability evidence, not proof of improvement. The historical single proposal is a migration reference, not a newly matched agent inference arm.

Synthetic scoring and geometry remain research approximations. PostgreSQL/container runtime verification requires those services; SQLite process recovery, mocked transport behavior and browser checks are independently testable locally.

## Observed live integration limits

The final runtime selects native JSON-schema output with automatic tool choice, the documented compatibility profile and mandatory inspection enforced outside the model. Current live probes are recorded in [the live capability report](live-evaluation.md). Two output-tool probes exhausted their 1,500-token bounds; the documented compatibility profile (`max_tokens`, omitted provider strict-tool flag, local Pydantic validation still strict) did not resolve function calling. A `NativeOutput` probe produced valid typed JSON but skipped the requested function. Discovery claims therefore do not establish a working tool loop. `provider.agent_loop_verified` is separate from the historical `live_verified` one-shot marker and remains false. No live promotion or learning improvement is claimed. The original failed attempt, every subsequent explicit probe, unknown billing and conservative reservations are retained.

The development evaluator has its own charged budget; trusted validation has at most four evaluations (strong static, FCFS, distinct accepted parent, frozen candidate). Those validation resources are reported separately and never exposed as feedback to the agent. `--replay PATH` in `scripts/evaluate_agent.py` re-evaluates previously frozen hashes without any new inference and records the source artifact hash and current evaluator configuration.
